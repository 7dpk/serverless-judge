# Deploying

There are two ways to deploy, and they read the same files: a folder under
`languages/` is a runner service, its `service.json` sizes it, and each
`langs/*.json` is a language. Pick one way for a given copy of the judge and
stay with it.

- [With Terraform](#with-terraform) (recommended)
- [With deploy.sh](#with-deploysh)
- [Adding packages](#adding-packages)
- [Adding a language](#adding-a-language)

## With Terraform

`terraform/` creates everything: the APIs, the image registry, the images
(built by Cloud Build, so you only need gcloud locally), three service
accounts, the Firestore database with its expiry rules, the Pub/Sub queue,
the 7-day log bucket, the Cloud Run services (the API, the worker and one
per folder of `languages/`) and the language registry.

```bash
gcloud auth login                         # used for the image builds
gcloud auth application-default login     # used by Terraform

cd terraform
terraform init
terraform apply -var project=<your-project-id>
```

The machine running `terraform apply` needs gcloud, bash and openssl,
because the image builds and the API key are local steps.

Put settings in `terraform.tfvars` (there's a `terraform.tfvars.example`):

| Variable | Default | |
|---|---|---|
| `project` | required | Project to deploy into |
| `region` | `us-central1` | Region for the services, the registry and the database |
| `families` | all | Deploy only some folders of `languages/`, for example `["python", "gcc"]` |
| `max_instances` | from `service.json` | Per-family instance cap, for example `{ gcc = 40 }` |
| `cpu_quota` | `200` | The regional CPU quota the caps must fit in (see [Capacity](performance.md#capacity-and-the-cpu-quota)) |
| `api_min_instances` | `0` | Keep API instances warm: no cold start, but an idle cost |
| `submission_ttl_hours` | `144` | How long submissions are kept |
| `allow_network` | `false` | Let a submission ask for network access with `enable_network` (see [Network access](api.md#network-access)) |
| `network_time_limit` | `30` | Seconds such a run may wait on the network, on top of its wall time limit |
| `max_network_time_limit` | `60` | The most a submission may ask for as `network_time_limit` |
| `max_download_mb` | `125` | The most such a run may download, and the largest file it may write |
| `name_prefix` | none | Run a second copy in the same project, for example `"staging-"` |
| `firestore_location` | the region | For a multi-region database such as `nam5` |
| `delete_data_on_destroy` | `false` | Let `terraform destroy` delete the database too |

### Getting the URL and the key

```bash
terraform output url
terraform output playground               # open this in a browser
$(terraform output -raw api_key_command)  # prints the key
```

The key is generated by a local step and stored in Secret Manager. It is
never written to the Terraform state.

### Changing things

Edit a package list, a `service.json` or add a language folder, then run
`terraform apply` again. Image tags are hashes of the files that go into
them, so only what changed is rebuilt and only the services that use it are
rolled.

### Removing it

`terraform destroy` deletes what it created. The database is left in place
unless `delete_data_on_destroy = true`, and the APIs stay enabled.

Two things linger after a destroy:

- Firestore reserves a deleted database's name for about 5 minutes, so wait
  that long before applying again under the same name.
- Cloud Logging keeps a deleted log bucket for 7 days. The next apply
  restores and reuses it.

### If apply stops part way

Run it again; it continues where it stopped. "Permission denied on secret"
or an HTTP 403 right after a deploy means an access grant hasn't taken
effect yet, which can take a few minutes.

### Things worth knowing

- **Scale to zero is set explicitly.** Every service has
  `min_instance_count = 0` and `cpu_idle = true`. The second one matters:
  without it Terraform deploys "CPU always allocated", which bills for the
  whole life of every instance.
- **Database access is scoped.** The API's service account gets its
  Firestore role with a condition that names the judge's own database, so
  the judge can share a project with other things that use Firestore.
- **Regions.** Any region with second-generation Cloud Run should work: the
  sandbox documentation listed no region limits when read on 14 November
  2026. It has been deployed and tested in `us-central1`, `us-east1`,
  `europe-west1` and `asia-south1`.
- **Versions.** Sandbox support was verified with version 8.11.0 of the
  `google-beta` provider, on Terraform 1.5.7.

### How it was tested

On 14 November 2026, by deploying separate copies from nothing next to the
`us-central1` one. The last of them, in `us-east1`:

- one `terraform apply`, 103 resources, 10 min 57 s;
- the live suite (`tests/e2e.py`, 70 checks) started the moment apply
  returned and passed;
- a second `terraform plan` showed no changes;
- none of its log lines reached the default 30-day bucket;
- `terraform destroy` removed all 103 resources in 74 s.

Earlier copies in `asia-south1` and `europe-west1` covered the rest: a
burst of 300 submissions all Accepted in 13.8 s, an apply interrupted by a
dropped connection and continued by running it again, and a destroy
followed by an apply under the same names (the log bucket was restored
automatically; the database name was free after 5 minutes).

On 15 November 2026 it went into a shared project that already ran 200
other Cloud Run services in `europe-west1`, with the Firestore API not yet
enabled: one apply, 103 resources, 11 min 2 s, the 70 checks passed, and a
second plan showed no changes. That run is also the test of the scoped
database role.

The five shared language services and network access came later, on 15 and
16 November 2026, and went to the `us-central1` copy with `deploy.sh`. The
live suite, by then 116 checks, passed there, the first runs on freshly
started instances included.

Not tested: a brand-new project (most of the APIs were already enabled
each time), a remote state backend, that the scoped role is refused on a
second database (none of the test projects had one), and the shared
language services and network access through Terraform, which has planned
them but not applied them.

## With deploy.sh

The same result with gcloud alone and no state file.

```bash
gcloud config set project <project>
./deploy.sh all            # infra, every language, the API
./deploy.sh lang python    # rebuild and redeploy one family
./deploy.sh api            # the API and the worker (one image)
./deploy.sh status         # URLs
./deploy.sh key            # the API key
```

Settings are environment variables, for example `REGION`, `QUOTA_VCPU`,
`API_MIN_INSTANCES` and, for network access, `ALLOW_NETWORK=1` with
`NETWORK_TIME_LIMIT`, `MAX_NETWORK_TIME_LIMIT` and `MAX_DOWNLOAD_MB`. The
runners and the API each keep their own network switch, so pass
`ALLOW_NETWORK` to every `deploy.sh` command of a copy that should have it.

One difference from Terraform: `deploy.sh` grants the API's Firestore role
on the whole project, not on the judge's database alone. In a project the
judge shares with other things, use Terraform.

## Adding packages

Edit the family's package list, then `terraform apply` or
`./deploy.sh lang <family>`.

| Family | File |
|---|---|
| python | `requirements.txt` |
| node | `package.json` |
| java | `packages.txt` (Maven `group:artifact:version`) |
| go | `packages.txt` (`module@version`) |
| rust | `Cargo.toml` |
| php | `composer.json` |
| gcc, script, functional, native | `apt-packages.txt` (Debian packages) |

C#, Swift and the languages in `jvm` have no package list yet.

## Adding a language

Create `languages/<family>/` with:

- `Dockerfile`: the toolchain, ending with the three lines every family
  shares (copy `/judge` and `/jexec`, copy `langs/`, set the entrypoint).
- `service.json`: CPU, memory and instance limits for the Cloud Run service.
- `langs/<name>.json`: how to compile and run. The fields are documented on
  `Manifest` in `runner/proto/proto.go`. `languages/php` is the smallest
  example; `languages/postgres` shows a language that needs a daemon.

Then `terraform apply` or `./deploy.sh lang <family>`. The API needs no
redeploy: it re-reads the registry when it meets an id it doesn't know.

A few things that were learned the hard way and are worth copying:

- **Test the image while it is built.** `languages/native/selftest.sh` and
  its siblings compile and run one small program per language as a build
  step, under the 1 MB file-size limit a judged program has. A language
  that doesn't work fails the build and never reaches a deploy.
- **A new folder is a new service**, and its `max_instances` counts against
  the CPU quota (see [Capacity](performance.md#capacity-and-the-cpu-quota)).
  A language that is asked for rarely is cheaper as one more `langs/*.json`
  in an image that already has room for it, which is why `script`, `jvm`,
  `functional` and `native` each hold several.
- **Runtimes that map a large file at start** die under the file-size
  limit. .NET needs `DOTNET_EnableWriteXorExecute=0` and the Erlang VM
  needs `+JMsingle true`; both are set in the manifest's `env`.
- **Runtimes with a slow start** can be given `runtime_cpu_ms`: CPU time
  that is added to the limit and taken off the reported time, so the
  program is judged on its own work. It is set for Elixir, Erlang, Clojure
  and Groovy, from what an empty program costs in a sandbox on an instance
  that has just started. That is when it costs most: Groovy used 2.8 s
  there against about 1.2 s warm.
